## Authority and maintenance

**Implementation check, 18 October 2026:** three new independent AI reviewers compared the current files with this register. They found confirmed gaps. The [alignment report](../docs/current-file-alignment.md) maps all 17 clauses to the inspected areas and states the limits of the review. It does not change the agreed rules below or claim that the application meets them all.

Current user decisions take precedence. An approved change replaces only the older requirements it explicitly changes. All other requirements remain in force. An implementation reference, an old diagram or a label saying that work was shipped does not authorize a policy change. Clarifying a requirement does not prove that a deployment meets it.

When a requirement changes, update its description, design, task, acceptance examples and affected user flows or reference documents together. Record who approved the change, its date and which older rule it replaces. Keep historical evidence with its original date and scope. The [requirements traceability matrix](RTM.md) lists the numbered specification packages; identify a rule by both its package and requirement number, such as 012/REQ-004.

## Required acceptance boundaries

- A guest can change filters and receive results within the public limits. If a detail page requires login, successful login returns the user to the detail they intended to open.
- A parent’s lesson payment or a dispute decision without payment cannot mark agency commission as received.
- Post approval, invitation acceptance and tutor selection do not release contact details. Test participant permission and the required match state separately.
- A contact change keeps the old value until confirmation succeeds. Expired, revoked or reused confirmation links must not change it. If revocation and confirmation arrive together, only one may take effect, with no partial update.
- A session-renewal response with status 429 leaves the browser’s cookies unchanged. Logout invalidates server-managed sessions without relying on page scripts to access protected cookies.
- Rescheduling an interview prevents an obsolete reminder from sending. Retrying after a crash must not save a second delivery request for the same recipient and the same version of the schedule. A changed meeting link reaches both participants under the agreed notification rules.
- Analytics test data includes recent records, records 31–90 days old, and records older than 90 days, for both posts and users. Each metric states which records it counts and which date determines inclusion.
- Reversing a release must not leave the running application trying to use a database table or relationship that has been removed. Delivery outages must preserve work that can be retried and make pending or permanently failed messages visible.

Every changed requirement needs a separate implementation check. Historical passing tests do not prove that a newly clarified acceptance example now passes.
