**Review date: 2026-09-05. Verdict: not fully aligned.** The main journeys are extensively specified, but the repository cannot yet serve as one consistent implementation contract. There are direct contradictions inside newer packages, older designs that were only partly updated after approved decisions, and acceptance criteria that do not prove their stated requirement. This is a document-alignment review, not a claim that every finding is a current application bug.

The two decisions you confirmed are controlling requirements: **guests may filter a limited public result set**, and **“commission paid” means the agency has received the tutor’s commission**. They do not need to be asked again.

## Scope and evidence

All **27 numbered packages and their 170 distinct namespaced requirements** were traced through their available specification, requirements, design, task and acceptance sections. The supporting review covers all **113 architecture/module/user interface documents**, all **43 numbered user-flow sequences**, and the **12 domain documents**. The report also checks operational/reference contracts and foundational product decisions. Long older documents were reviewed through normative clauses, acceptance sections and amendments; historical code examples and old screenshots were not exhaustively revalidated.

The [170-row requirement matrix](alignment/requirements-matrix.md) records a result and source links for every named requirement. The [file coverage register](alignment/coverage.md) distinguishes full primary-document review, targeted supporting review, historical evidence and inventory-only files. The [original catalog](catalog.md) also indexes the older product requirements document/business requirements document features and rules; these overlap the numbered requirements and are not additional unique requirements.

Authority order used: current user decision → explicit approved amendment for the affected clause → retained requirement → design/tasks → descriptive implementation reference. A later date or HISTORICALLY MARKED IMPLEMENTED header alone does not approve a policy change. A recorded supersession resolves which rule applies, but stale actionable instructions still need correction.

## What is settled, and what remains unclear

The following are document corrections with an existing decision: anonymous filtering; agency receipt for PAID; completion on PAID; contact release restricted to assigned participants and retained match-state/user interface gates; optional tutor listing for free-market applications; phone changes confirmed through the account email; the 30-minute user-session/refresh model; distinct N LEVEL taxonomy; 007 replacing the old reminder sweep; and 027 disabling production one-time passcode logging. Preserve each amendment’s scope rather than deleting all older requirements.

The remaining decisions or missing contract details are narrower:

- **Invitations on PENDING posts:** initiation is approved, but acceptance before approval still conflicts with the older ACTIVE-only acceptance flow. Define what happens if a tutor accepts first, and test rejection/closure cleanup. Rejection cleanup itself is already required by 021. [021 review](alignment/numbered-019-027.md).
- **Average commission:** 017 explicitly leaves the exact date cohort to the business owner. 019’s statement that code is correct does not supply that definition. [017 requirement](../../017-admin-analytics-and-financial-safety/requirements.md).
- **Consent and contact-change contracts:** settle which policy version is recorded when the displayed page and server version differ; specify the already-required warning/revoke mechanism. This is more precise than reopening whether consent or confirmation is needed. [001 review](alignment/numbered-001-009.md); [012 review](alignment/numbered-010-018.md).
- **Commission inputs and exceptions:** activation is already the approved lock point. The exact first-month calculation/rate guard and broader early-ending, partial-receipt and dispute/replacement scenarios still need the reconciliation described in the earlier audit. Do not infer that marking agency commission paid means teaching has ended. [Lifecycle audit](audit.md).
- **Missing decision records:** 020/025 need the approved canonical taxonomy/mapping record; 027 needs its approved plan restored. These are evidence gaps, not proof that approval never happened. [019–027 review](alignment/numbered-019-027.md).
- **Checkable outcomes:** 026 says the parent wizard’s “2 hours default” is reviewed without recording the resulting behavior. Error fallback wording, trace Id collision handling and scheduler rescheduling guarantees also need one unambiguous outcome. [026 review](alignment/numbered-019-027.md); [010/016 review](alignment/numbered-010-018.md).

## Correction order

1. Create one current decision table for public access, contact release, consent/contact changes, session behavior and money events. Link each superseded clause to its replacement. requirements traceability matrix currently stops at 010; extend the maintained index to 027.
2. Correct contradictory design/task instructions in 004, 011, 012, 014 and 025, then the supporting migration, application programming interface and operational references. These corrections follow existing decisions.
3. Repair acceptance scenarios: analytics cohorts, seed minimums, invitation approval/rejection, contact revoke, reminder deduplication/rescheduling and taxonomy rollback. Each scenario should show pre-state, action and post-state, plus relevant permission/negative cases.
4. Record the remaining policy definitions and recover missing approval artifacts. Then reconcile application behavior against that coherent baseline; document alignment alone cannot certify launch readiness.
